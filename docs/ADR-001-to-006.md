# ADR-001: Modular Monolith over Microservices

**Status:** Accepted
**Date:** 2025-04
**Deciders:** Sparsh Khandelwal

## Context

FitAI starts as a single-developer project. We need an architecture that avoids premature complexity, can be understood and debugged by one person, yet does not create a big ball of mud that requires a full rewrite when the user base grows.

The classic tension: microservices give you independent deployability and scaling but add massive operational overhead (service discovery, distributed tracing, inter-service auth, network latency, eventual consistency). A traditional monolith is simple but turns into spaghetti without discipline.

## Decision

**Modular monolith** — a single deployable unit with hard domain boundaries enforced through code structure, not network calls.

Directory enforcement:
```
apps/api/src/
├── auth/
│   ├── auth.module.ts      ← NestJS module boundary
│   ├── auth.controller.ts
│   ├── auth.service.ts
│   └── auth.repository.ts  ← ONLY domain that touches auth tables
├── workouts/
│   └── ... (same pattern)
```

**Rule:** No domain imports another domain's service or repository directly. Cross-domain communication happens only through:
1. Shared DTOs (in `libs/shared/`)
2. Internal events via EventEmitter2
3. The domain's public module exports

## Alternatives considered

| Option | Pros | Cons |
|---|---|---|
| Microservices from day 1 | Independent scaling, deployment | 10× operational complexity, distributed tracing needed, network latency on every call, impossible to run locally without k8s/compose complexity |
| Traditional monolith | Simple | No path to scaling, tech debt compounds, impossible to extract later |
| **Modular monolith** (chosen) | Simple deployment, extractable later, locally runnable, fast inter-domain calls | Single process (CPU-bound work blocks if not offloaded to queue — mitigated by BullMQ for AI calls) |

## Consequences

**Positive:**
- Single `docker compose up` runs everything locally
- No distributed tracing needed until Phase 2
- Each domain can be extracted to a microservice by: (a) creating a new service, (b) replacing EventEmitter with Redis pub/sub, (c) redirecting imports — all with no interface changes
- Easier to reason about data consistency (single transaction boundary)

**Negative:**
- Single deployment unit — a bug in one domain can crash all (mitigated by NestJS exception filters and process managers)
- Cannot independently scale domains until extraction (mitigated by Cloud Run auto-scaling the whole service)

**Review trigger:** Extract `ai-coach` domain when Claude API calls constitute >30% of total request latency or when team size exceeds 2 engineers.

# ADR-002: Next.js 14 over Angular or Plain React

**Status:** Accepted
**Date:** 2025-04

## Context

The frontend must: (1) work as a PWA installable on Android, (2) load fast on mobile networks in India, (3) support streaming AI responses (SSE), (4) be developer-friendly for a TypeScript-first engineer.

## Decision

**Next.js 14 with App Router.**

## Alternatives considered

| Option | Pros | Cons |
|---|---|---|
| Angular | Strong DI, RxJS for streams, familiar (NIQ stack) | Larger bundle size, steeper SSR setup, PWA support requires `@angular/pwa` extra config, not ideal for React-ecosystem AI libraries |
| Create React App / Vite + React | Familiar, simple | No SSR, poor initial load on mobile, no PWA primitives built-in, deprecated (CRA) |
| **Next.js 14** (chosen) | App Router RSC reduces JS bundle, built-in PWA via `next-pwa`, streaming RSC for AI, Image optimization, TypeScript first-class | More complex mental model (RSC vs Client Components), App Router caching can surprise |
| Remix | Excellent data loading, progressive enhancement | Smaller ecosystem, less AI/streaming library support |

## Decision rationale

- **React Server Components** allow the workout dashboard shell to render with zero JS — the component tree is HTML by default, only interactive parts hydrate. On a 4G Indian connection, this shaves 1–2 seconds off LCP.
- **Streaming** — Next.js natively supports React `Suspense` streaming, which pairs with our SSE-based AI chat to show partial responses as they arrive.
- **PWA** — `next-pwa` (Workbox-based) gives us service worker, offline cache, and install-to-home-screen in ~20 lines of config.
- **Ecosystem** — `ai` SDK from Vercel, `@anthropic-ai/sdk`, React Query, Zustand all have first-class Next.js support.

## Consequences

- Server Components must never use browser APIs (localStorage, window) — enforced by `'use client'` directive. New discipline required.
- App Router caching behavior (full route cache, data cache, request memoization) must be explicitly understood — documented in component spec.
- TypeScript strict mode enabled from day 1, no exceptions.

# ADR-003: PostgreSQL 16 + Redis 7

**Status:** Accepted
**Date:** 2025-04

## Context

Need a primary data store for structured relational data (users, workouts, nutrition) and a fast cache/queue layer. The data model has clear relationships (user → plans → sessions → sets) that benefit from relational integrity. Future ML features require storing high-dimensional embeddings for semantic workout search.

## Decision

**PostgreSQL 16 as primary store, Redis 7 as cache + queue.**

ORM / query builder: **Kysely** (type-safe SQL, no magic, same as NIQ production stack).

## Alternatives considered

| Option | Verdict |
|---|---|
| MongoDB | Rejected — workout sets are relational, schema flexibility not needed, harder to query aggregates (total weekly volume, progressive overload trends) |
| MySQL | No `pgvector`, less rich JSON support, inferior window functions for trend queries |
| DynamoDB | Good for scale, terrible for ad-hoc analytics, no joins means workout dashboard queries become N+1 nightmares |
| Prisma over Kysely | Prisma adds magic — generated client hides SQL, hard to optimize, migration friction. Kysely is SQL in TypeScript: explicit, debuggable, zero runtime magic |
| **PostgreSQL + Kysely** (chosen) | ACID, window functions for PR detection, `pgvector` extension ready for future ML, JSONB for flexible exercise metadata |

## pgvector rationale

`pgvector` extension enables storing workout plan embeddings. Future use case:
```sql
-- "Find the 5 most similar users to me by training profile"
SELECT user_id, profile_embedding <=> $1 AS distance
FROM user_fitness_profiles
ORDER BY distance
LIMIT 5;
```

This powers the future recommendation system without adding a separate vector database (Pinecone, Weaviate) until scale demands it.

## Redis data model

```
Key pattern                    TTL        Purpose
user:{id}:session              24h        JWT session validation
user:{id}:ai-context           60m        Assembled Claude context (layers 1-2)
user:{id}:session-summary      10m        Last 7 days workout summary
queue:ocr                      —          BullMQ OCR job queue
queue:plan-generation          —          BullMQ async plan generation
ratelimit:{ip}                 1m         Sliding window rate limiter
```

# ADR-004: Layered Prompt Caching Context Strategy

**Status:** Accepted
**Date:** 2025-04

## Context

Claude API pricing is token-based. A naive implementation that sends full user history + all workout logs + conversation history on every chat request would cost ~$0.05–0.20 per message per user (100k+ tokens). At 10,000 users sending 10 messages/day, that is $5,000–20,000/day. Unsustainable.

More importantly: Claude's context window is 200k tokens. The question is not "what can we fit" but "what is the minimum necessary context to give a useful, personalized response."

## Decision

**Five-layer context assembly with differential caching.**

```
Layer 0: System persona         ~400 tokens   Cache: permanent (never changes)
Layer 1: User profile + goals   ~800 tokens   Cache: 1 hour (Redis key: user:{id}:ctx:profile)
Layer 2: 30-day training summary ~1200 tokens  Cache: 30 min  (Redis key: user:{id}:ctx:summary)
Layer 3: Last 7 days detail     ~2000 tokens  Cache: 10 min  (Redis key: user:{id}:ctx:recent)
Layer 4: Today's active session ~500 tokens   Cache: none    (always fresh)
Layer 5: Conversation history   variable      Cache: Redis   (last 20 messages, ~3000 tokens)

Total typical context: ~8000 tokens per request
```

Claude's prompt caching API (`cache_control: { type: "ephemeral" }`) is applied at Layer 1 boundary. Anthropic caches the prefix up to that boundary for 5 minutes, giving ~90% token reduction on repeated messages.

## Context assembly algorithm

```typescript
async buildContext(userId: string, sessionId?: string): Promise<ClaudeMessage[]> {
  const [profile, summary, recent, session, history] = await Promise.all([
    this.cache.getOrFetch(`user:${userId}:ctx:profile`, 3600,
      () => this.buildProfileLayer(userId)),
    this.cache.getOrFetch(`user:${userId}:ctx:summary`, 1800,
      () => this.buildSummaryLayer(userId)),
    this.cache.getOrFetch(`user:${userId}:ctx:recent`, 600,
      () => this.buildRecentLayer(userId)),
    sessionId ? this.buildSessionLayer(sessionId) : null,
    this.conversationRepo.getRecent(userId, 20),
  ]);

  return assembleWithCacheControl([profile, summary, recent, session], history);
}
```

## Token budget enforcement

Hard limit: 16,000 tokens total context per request.
If `recent` layer exceeds 2,000 tokens (user has many sessions), it is summarized via a cheaper Claude Haiku call first.
Conversation history uses sliding window — oldest messages dropped when budget exceeded.

## Consequences

**Positive:** ~80% cost reduction vs naive implementation. Personalized responses without full history on every call.
**Negative:** Stale context possible within cache TTL window (user updates goal, AI still uses old goal for up to 1 hour). Mitigated by explicit cache invalidation on profile update events.

# ADR-005: EventEmitter2 for Intra-Domain Communication

**Status:** Accepted
**Date:** 2025-04

## Context

Domains need to react to each other's events without tight coupling. Example: when a workout session completes, the nutrition domain needs to adjust calorie targets, and the AI coach domain needs to invalidate its context cache. If nutrition imports WorkoutService directly, we create circular dependencies and tight coupling.

## Decision

**NestJS EventEmitter2** (in-process event bus) with typed event contracts.

All events defined in `libs/shared/events/`:
```typescript
// libs/shared/events/session-completed.event.ts
export class SessionCompletedEvent {
  constructor(
    public readonly userId: string,
    public readonly sessionId: string,
    public readonly totalVolumeKg: number,
    public readonly durationMinutes: number,
    public readonly exerciseCount: number,
  ) {}
}
```

## Extraction path to message broker

When extracting `ai-coach` to a separate service:
1. Replace `@OnEvent('session.completed')` decorator with a Kafka/SQS consumer decorator
2. Replace `this.eventEmitter.emit(...)` with a message producer client
3. Event payload interface: **unchanged**

This is a deployment concern, not a code rewrite. Other domains do not change.

## Alternatives considered

| Option | Verdict |
|---|---|
| Direct service injection across domains | Rejected — creates circular dependencies, tight coupling, defeats modularity |
| Redis pub/sub from day 1 | Over-engineered — adds network hop, serialization, error handling complexity for in-process events |
| Kafka from day 1 | Extremely over-engineered — Kafka requires ZooKeeper/KRaft, adds significant infrastructure complexity |
| **EventEmitter2** (chosen) | In-process, typed, zero infrastructure, clear extraction path |

# ADR-006: PWA over React Native for Mobile

**Status:** Accepted
**Date:** 2025-04

## Context

The app must work on mobile (primary use case is in the gym). Options: (1) build a native iOS/Android app, (2) use React Native, (3) use Expo, (4) build a Progressive Web App.

## Decision

**PWA via Next.js + `next-pwa` (Workbox).**

## Rationale

| Criteria | PWA | React Native / Expo |
|---|---|---|
| Single codebase | ✓ Web + mobile same code | ✗ Separate RN codebase |
| App Store deployment | ✓ Play Store via TWA | ✓ Native app stores |
| Lock screen widget | Partial (Android Shortcut API) | Full native widget |
| Camera / photo access | ✓ Web APIs | ✓ Native |
| Offline support | ✓ Service Worker | ✓ Native |
| Dev complexity | Lower | Higher (two platforms) |
| Portfolio value | Shows PWA skill | Shows RN skill |

**Decision driver:** We are one developer. Maintaining a separate React Native codebase doubles the surface area. The PWA approach delivers 90% of the native experience for 30% of the effort.

**Play Store path (TWA — Trusted Web Activity):**
Google Play allows publishing a PWA as an Android app via TWA with no code changes:
```bash
bubblewrap init --manifest https://fitai.app/manifest.json
bubblewrap build  # generates signed APK
# Upload APK to Google Play Console
```

**Lock screen widget limitation:**
True native lock screen widgets require a native layer (Kotlin/Swift). Mitigation:
- Android home screen widget via TWA + Web App Manifest `shortcuts` array
- Today's workout shown as a notification-style persistent alert (Android notification channel)
- Full native widget deferred to Phase 3 if demand warrants Capacitor.js wrapper

## Consequences

- No native lock screen widget at launch (home screen shortcut instead)
- Camera access works in modern browsers via `getUserMedia` / `<input type="file" accept="image/*" capture="environment">`
- Offline: service worker caches today's workout plan and allows check-in logging while offline, syncs when connection restores
